# MiuList 局域网同步协议（v3）

> 手机 App 与网页端**对等**，各自持有一份完整快照，都能独立运行。
> 同步时**由用户选方向**；两端都在线且没有冲突时自动同步。
> 传输全程**签名 + 密文**。

---

## 1. 为什么要「双端快照」而不是「手机当主机、网页端当镜像」

镜像模型下，网页端离开手机就不能用 —— 它的每一行数据都是手机给的。
于是「手机上删了一条待办」这类事，网页端要么看不到，要么被静默改写。

对等模型下：

| | 手机 App | 网页端 |
|---|---|---|
| 快照存哪 | Room（`/data/data/.../databases`） | 浏览器 localStorage |
| 断网能用吗 | 能 | **能**（打开就有数据，改了先记着） |
| 能改吗 | 能 | 能 |
| 谁是权威 | 取决于用户选的方向 | 同左 |

「权威」不是一个固定的东西，而是**每次同步时用户选的方向**。

### 网页端跑在哪里：三种方式

**接口服务端永远是手机**（协议里所有 `/api/*` 都在手机上）。
变的只是**网页端由谁托管**：

| | 托管方 | 页面地址 | 什么时候用 |
|---|---|---|---|
| **单文件桌面端（beta）** | 无本地服务；Chrome / Edge 直接打开 HTML | `file:///…/MiuList-Web.html` | **桌面端主用法**：手机不在也能看能改；地址填一次；本地快照是 localStorage + 可选 JSON |
| 手机托管 | 手机既提供接口也提供网页文件 | `http://192.168.x.x:手机端口/` | 手机上开着局域网服务时，手机扫别的设备也能直接打开 |
| **电脑端启动器（已退役）** | 电脑上一个本地服务只托管网页文件 | `http://127.0.0.1:8777/` | 旧版；会触发 Windows 未签名应用提示，beta 起由单文件桌面端取代 |

三种方式用的是**同一套同步协议**，网页端代码里只有两处不同：「接口地址从哪来」与「本地快照存哪」。

**单文件桌面端（beta 起）**：

- 页面由浏览器从 `file://` 打开，没有本地 HTTP 服务；
- 手机地址由**人**搬一次：手机上「网页同步」点「复制连接链接」→ 电脑上「粘贴」，
  或者直接手打；记在 localStorage；
  **浏览器不能发 UDP 广播**，但能**扫网段**（见下）；
- 本地快照在浏览器 localStorage；可额外绑定一个本机 **JSON 文件**做镜像，
  文件**不含配对密钥**；
- 首次配对：**挑一条路，各只做一个动作** ——
  「手机扫电脑的码」或者「只填地址、手机上点允许」；
  之后打开即自动同步。

### 找到手机：扫网段（浏览器能用的那条）

> 旧启动器用 UDP 广播（见下），**浏览器做不到**。单文件桌面端用的是「挨个敲」。

手机在局域网里监听的是**固定端口** `38780`（被占用就往后顺延到 `38784`）——
端口固定，电脑才知道该敲哪儿。

电脑上记着上次连过的地址（`http://192.168.1.20:38780`），
连不上时就**扫一遍那个 /24**：`192.168.1.1` … `192.168.1.254`，
每个地址先试 `38780`，不通再试下一个端口。探针是 `GET /api/health`，
回的不是 MiuList 就跳过（`web/discovery.js`，node 可直接跑自检）。

- 扫一轮 ≈ 254 个请求，并发 24、单个超时 800ms，**找到就停**；
- 手机的 IP 变了（DHCP 换地址）也能找回来 —— 用户什么都不用做；
- 扫的只有**地址**：`/api/health` 里没有密钥，也没有任何数据内容。

> **配对只做一件事**：两条路**各**只多一个动作，不掺和。
>
> | 路 | 用户做的 | 公钥走哪条通道 |
> |---|---|---|
> | **扫码** | 手机扫电脑上那张码（地址已经知道了） | 二维码（视觉通道） |
> | **只填地址** | 把手机地址填/粘进来 | HTTP（**公钥不是秘密**） |
>
> 两条路的**密钥都是两端各自算出来的，从不过网**（见 §2 的 DH 协商）——
> 所以「只填地址」并不比扫码弱。

> **旧的「电脑端启动器」（`tools/pc-web/`）已经退役**：它用本地服务托管网页、
> UDP 自动发现手机、DPAPI 加密镜像，并且会触发 Windows 的「未知发布者」。
> 下面与启动器 / UDP / DPAPI 有关的段落只用于理解旧版；beta 桌面端不用。

桌面端（单文件的 `file://`，或旧启动器的 `127.0.0.1`）与手机的 `192.168.x.x` → **跨源**。
为此手机上那个 HTTP 服务要额外做四件事（少一件就是「同源正常、跨源连不上」）：

1. 预检回显 `Access-Control-Allow-Headers`，且**包含 `X-ML-*` 那几个签名头**；
2. 回显 `Access-Control-Expose-Headers: X-ML-Enc` ——
   跨源时自定义响应头默认对脚本不可见，而这个头是「**这坨是密文**」的标记，
   少了它网页端会把密文当明文 JSON 解析；
3. **SSE 响应也要带 CORS 头** —— `EventSource` 是跨源的，缺了这条流会被浏览器掐掉；
4. **Private Network Access** —— 从 `file://` 访问局域网手机时，Chrome 的预检可能带
   `Access-Control-Request-Private-Network: true`，服务端要回
   `Access-Control-Allow-Private-Network: true`（手机与 mock 已实现）。

### 找到手机：UDP 广播探测（旧启动器）

> **beta 单文件桌面端不用这一节**：浏览器不能发 UDP，地址从手机屏幕上的
> 地址二维码扫入或手动填。手机的 UDP 发现口保留给旧启动器。

手机的 HTTP 端口是**随机的**（`LanHttpServer(port = 0)`，免得跟电脑上别的服务撞端口），
所以「按固定端口找手机」这条路走不通。

于是手机在开着局域网服务时，额外开一个**固定端口的 UDP 探测口**：

```
电脑端                                        手机
  │ 广播 UDP:38777  "MIULIST-DISCOVER/1"        │
  │ ───────────────────────────────────────────►│
  │                          应答 {"app":"MiuList","port":<HTTP 端口>,
  │                                 "deviceName":"…","appVersion":"…"}
  │ ◄───────────────────────────────────────────│
  │ 于是知道该往 http://192.168.x.x:<port> 发请求 │
```

- 探测端口固定（`38777`），电脑端要能预先知道往哪儿发；
- 手机的 HTTP 端口随机，由应答告诉电脑端；
- 应答里**只有地址，没有密钥**，也没有任何快照内容。

手机不在同一个网段时广播到不了 —— 旧启动器里手动填地址；
新桌面端本来就用地址二维码/手动填，跨网段也能用。

## 2. 配对：DH 协商（密钥从不过网）

> **v3.2**。v3 的做法是「secret 只走视觉通道」—— 密钥从二维码搬过去。
> 这条性质很好，但它让「手动填地址」走不通：光有地址，电脑拿不到 secret，
> 配对就停在半路。
>
> v3.1 换成 **DH 密钥协商**：两端交换**公钥**，各自算出**同一把共享密钥**。
> **过网的只有公钥** —— 公钥本来就是公开的东西，抓包的人看到它也算不出密钥。
>
> v3.2 在此之上补了三件事：**配对码转录绑定**（`H(A‖B)`，见下）、
> **退化公钥拒收**、**配对码强制比对**。

```
网页端                                         手机
  │ 生成临时密钥对 (a, A = g^a mod p)               │
  │ A 是公钥 —— 不是秘密                             │
  │                                                 │
  │ ── 扫码路 ──                                    │
  │ 二维码 miulist://pair?v=5&k=<A>&r=<requestId>    │
  │              用户用手机相机扫 → 唤起 App ──────► │
  │                                                 │
  │ ── 只填地址路 ──                                 │
  │ POST /api/pair/request {requestId, deviceName,  │
  │                        publicKey: A}             │
  │ ──────────────────────────────────────────────► │
  │                                                 │
  │                     手机生成 (b, B = g^b mod p)  │
  │                     S = A^b mod p = B^a mod p    │
  │                     secret = sha256(S)           │
  │                     弹**一张**确认卡：显示配对码  │
  │                     用户点「允许」                │
  │                                                 │
  │ GET /api/pair/status?requestId=…（轮询）         │
  │ ──────────────────────────────────────────────► │
  │ ◄── {state:"approved", deviceId, publicKey: B,   │
  │      pairCode:"7K2M9Q"} ──────────────────────► │
  │                                                 │
  │ S' = B^a mod p；核对 pairCode；secret = sha256(S')│
```

### 密钥为什么从不过网

抓包能看到的只有：`A`、`B`、`requestId`、配对码。

- `A`、`B` 是**公钥**：知道它们也算不出 `S`（DH 的单向性）；
- 唯一能算出 `S` 的是**持有私钥的那一端**（`a` / `b`），而私钥从不出机器；
- 于是「只填地址」这条路也不必把密钥放上网 —— 它放的只是一个公钥。

**换来的好处**：两条路（扫码 / 只填地址）的密钥安全性**完全一样**，
用户选哪条路不用在「省事」和「安全」之间取舍。

### 配对码：两端一致，让用户能核对

```
pairCode = sha256("miulist-paircode-v3.2" ‖ A ‖ B) 的前 6 位（Crockford base32）
```

- `A` = 发起方（电脑）的公钥，`B` = 响应方（手机）的公钥，**顺序不能反**；
- 两端都拿得到 `A` 与 `B`，所以都能算这个码；
- 字母表去掉 `I / L / O / U`，避免和 `1 / 0` 混淆；
- **v3.2 改过**：v3.1 只哈希了 `A`（发起方自己的公钥）——
  它能证明「我看到的 A 跟你看到的一样」，但**证明不了对面是谁**。
  改成 `H(A‖B)` 之后，中间人换掉**任何一个**公钥，两端算出的码就对不上；
- 网页端**强制比对**：手机报上来的 `pairCode` 必须**存在**且与自己算的一致，
  缺一即**直接中止配对**。（v3.1 这里的判断是 `if (res?.pairCode && ...)`，
  响应里缺这个字段时整个校验会被跳过 —— 等于形同虚设。）

### 参数与实现

| 项 | 值 |
|---|---|
| 群 | RFC 3526 §3 的 **2048 位 MODP 群（group 14）**，生成元 `g = 2` |
| 私钥指数 | 256 位随机（2048 位群配 256 位指数 ≈ 128 位安全强度） |
| 共享值编码 | 定长 **256 字节**（大端、高位补零）→ `sha256` → 32 字节 secret |
| 实现 | 网页端 `web/crypto.js`（BigInt）／手机端 `WebDh.kt`（BigInteger） |

**为什么不用 ECDH**：

- 网页端可能跑在 `http://192.168.x.x` 上（手机托管网页端那条路）——
  那不是 secure context，`crypto.subtle` 是 undefined，**连密钥协商都做不了**；
- 手机端 `KeyAgreement("ECDH")` 在各家 Android 厂商的 JCE 上行为并不一致
  （老版本 AndroidOpenSSL 干脆不注册 ECDH）。

而 **BigInt / BigInteger 两边都有**，实现只有一份逻辑。

**两端必须逐字节一致** —— `web/crypto.test.mjs` 与 `WebDhTest` 用**同一组向量**
（私钥 → 公钥 → 共享密钥 → 配对码）对齐。对不上的症状是
「配对显示成功、之后每次请求都解密失败」。

### 派生

```
effective = passcode 为空 ? secret : HMAC-SHA256(secret, "miulist-pw-v3" + passcode)
master    = HMAC-SHA256(effective, "miulist-master-v3")
kEnc      = HMAC-SHA256(master, "miulist-enc-v3")    // ChaCha20 密钥
kAuth     = HMAC-SHA256(master, "miulist-auth-v3")   // 请求签名
kMac      = HMAC-SHA256(master, "miulist-mac-v3")    // 密文 MAC
```

- 标签（label）分开，是为了让同一把 secret 在不同用途上不产生相同的子密钥。
- **kMac 必须与 kEnc 不同**：流密码的密钥复用会毁掉整个结构（用它认证等于用同一把钥匙既锁又签）。
- 同步密码（4 位数字）会**先混进 secret** —— 于是「二维码被别人拍到」也不足以解密。
  代价要说清楚：4 位数字只有 10⁴ 种，拿到 secret 的人可以离线毫秒级爆破它。
  它挡的是「旁边有人瞄到屏幕」，不是密码学意义上的第二因子。

### 配对请求的规则

- 配对请求 5 分钟过期、**一次性**：批准后这个码立刻作废。
- token 不再存在 —— 每设备一把密钥，可单独撤销。
- **老协议（v3）仍然认**：深链 `miulist://pair?v=3&s=<secret>&r=<requestId>`
  （v3.2 只在 `v=5` 这条路上改了配对码算法，老协议那条不受影响；
  但**新版桌面端不再走老协议** —— 它要求手机报 `pairing: 5`）
  里的 secret 走视觉通道，手机照样能批准（旧网页端 ↔ 新手机）。
  反过来（新网页端 ↔ 旧手机）网页端会先问 `/api/health` 里的 `pairing` 字段，
  旧手机没有这个字段 → 网页端退回扫码那条老路。

### 两条通道的先后顺序无关紧要

同一个配对请求有两条通道进到手机上：

| 通道 | 带来什么 | 什么时候到 |
|---|---|---|
| `POST /api/pair/request` | `requestId`；**只填地址路**还带公钥 `A` | 电脑出二维码之前 |
| 深链 `miulist://pair?v=5&k=<A>&r=…` | 公钥 `A` | 手机扫到二维码的那一刻 |

手机上收到任何一条都会**补齐 pending 记录**（若还没有），
所以「深链先到、请求后到」与「请求先到、深链后到」都能批准 ——
批准与否只取决于**用户点了什么**，不取决于两条通道谁先跑完。

**只有拿到公钥（或者老协议的秘密）才弹确认卡** ——
否则用户看到的是一张「有个请求」，却连配对码都算不出来。

## 3. 请求：挑战-应答签名

每个请求带四个头：

```
X-ML-Device: <deviceId>
X-ML-Ts:     <epoch 毫秒>
X-ML-Nonce:  <一次性随机串>
X-ML-Sig:    <base64url(HMAC(kAuth, "v3\nMETHOD\n/path\nts\nnonce\nbase64url(sha256(body))"))>
```

抓包拿到 sig **用不了**：

- **不能重放** —— nonce 每个请求随机，服务端记着「用过的 nonce」，同一个只能用一次；
- **不能伪造** —— 没有 kAuth 就算不出新的 sig；
- **不能挪到别的设备** —— deviceId 在签名之外也被校验；
- **不能换方法/路径/请求体** —— 它们都在签名覆盖范围内。

时间戳窗口 ±90 秒再挡掉「隔天重放」。

SSE（`/api/events`）用**查询串**带同样四个参数 ——
EventSource 不能设请求头，这是唯一的例外。

## 4. 负载：密文

请求密文放在 **HTTP body** 里（原始 sealed 字节，`X-ML-Enc: 1` 标记）；
响应密文也在 body 里（base64url，`X-ML-Enc: 1` 标记）。

**不要把密文塞进请求头。** 手机侧的请求头限制 16 KB，而一份带周课表的快照
轻松超过这个数；放头里会让连接被顶断，浏览器只会报一个看起来像 CORS 的失败。
beta 起只保留 body 这一条传输。

```
plaintext ──ChaCha20(kEnc, nonce)──► ciphertext
                     │
                     └──► MAC = HMAC-SHA256(kMac, nonce ‖ ciphertext)
sealed = nonce(12) ‖ ciphertext ‖ MAC(32)
```

**先加密再认证（encrypt-then-MAC）**：解密前先验 MAC，不对就拒。

- 算法：**ChaCha20 + HMAC-SHA256**。
  - 为什么不用浏览器自带的 `crypto.subtle`？它在**非 secure context 里不存在**，
    而我们的网页端是手机在局域网里用 `http://192.168.x.x` 直接发的 ——
    那个页面不是 secure context，`crypto.subtle` 是 undefined。
  - 为什么不用 AES-GCM？它的 GHASH 在 JavaScript 里没有 64 位运算，
    只能靠 BigInt 或拆 32 位对，又慢又容易写错；ChaCha20 的核心只有
    加法/异或/旋转，能用 **RFC 8439 官方测试向量**逐位验证，
    而且手机端与网页端能实现同一份逻辑（见 `web/crypto.js` 与 `WebCrypto.kt`）。
- 两端实现必须**逐字节一致** —— 密钥派生标签、密文格式、MAC 覆盖范围全都要对齐。
  `web/crypto.test.mjs` 与 `WebCryptoTest` 用同一组向量交叉验证。

## 5. 同步的规则

| 情况 | 行为 |
|---|---|
| 两端都在线 **且没有冲突** | **双向自动同步**，不用点任何东西 |
| 有一端离线 | 手动选方向 |
| 同一条待办两边都改过 | 手动选方向，并提示**两端快照的最新编辑时间** |

### 两条落库路径

`POST /api/snapshot/apply` 的请求体：

```jsonc
{
  "mode": "merge" | "replace",
  "snapshot": { /* 一份完整的快照 */ }
}
```

- **`merge`（增量）** —— 自动同步走这条：只把对方给的那几条按「后写覆盖」并进来，
  其余一概不动，**不删任何东西**。
  双方都没冲突时，只传各自改过的那几条就够。
- **`replace`（整份）** —— 手动选方向走这条：本机整体换成对方那一份。
  **删除能传播全靠它** —— 增量路径分不清「对方没有这条」是「还没同步」还是「被删了」。

### 护栏：三个 `hasXxx` 标记

课程 / 考试 / 自定义分类各自带一个 `hasXxx`：
**这一块是有效内容，还是这一端还不知道。**

网页端**还没成功拉过一次**手机数据时，它的快照里这三块是空的 ——
那不是「手机上没有课程」，而是「网页端还不知道」。没有标记就照单全收，
会把手机上的课表整个清空 —— 而「刚打开网页端就点同步」最容易踩这个坑。

### 两端各管各的课表

**网页端是独立的一端，不是手机的镜像。**

- 自动同步只交换**待办**：网页端的推载荷默认**不带**这三个标记
  （`hasCourses` / `hasExams` / `hasTaskTypes` 都是 false），
  手机收到就**保留自己的课表**，不会被网页端那份换掉。
- 反过来也一样：网页端拉手机快照时，也**不拿**手机的课表覆盖自己那份。
- 要搬配置是**显式**动作（网页端「同步 → 连接」里的两个按钮）：
  - 「用手机的课表和考试」→ 一次 GET，把配置搬进本机；
  - 「把本页课表推给手机」→ 一次 apply，载荷带标记、**且 `tasks` 为空**
    （手机侧待办一条都不动，只换课表/考试/分类）。

**远端不带课表时，待办仍然要挂到课程上。**
网页端推过来的待办带着 `courseKey`（自然键 `代码|名称|教师`，跨端通用），
手机按这个键查**自己**的课就能挂上（`SnapshotApplier.linkToLocalCourses`）。
否则每一条带课程的待办都会落成「未关联课程」——
用户看到的是「手机上这条待办突然没有课」。

### 快照里的周课表（`timetable`）

网页端课表页有一张**周课表栅格**：七列 = 这一周里真实的七个日期，
每列按节次排着当天的课与考试。它随快照一起走，形状是：

```jsonc
"timetable": {
  "totalWeeks": 16,          // 学期总周数（翻周箭头的上界）
  "currentWeek": 11,         // 当前周次
  "periodsPerDay": 13,       // 一天几节
  "periods": [{ "period": 1, "startMinute": 480, "endMinute": 525 }],
  "slotList": [{             // 去重后的全部时段，周计划里按下标引用它
    "courseKey": "PHYS1001|大学物理|王芳",
    "startPeriod": 3, "endPeriod": 4, "classroom": "教十 201"
  }],
  "weeks": [{
    "week": 11,
    "days": [{
      "date": "2026-10-26",  // 这一列是**真实日期**，不是星期几
      "dayOfWeek": 1,
      "offReason": null,      // NO_CLASS / VACATED / WEEKEND / OUT_OF_TERM
      "makeupDayOfWeek": null,// 补课日：补的是星期几的课
      "slotIndexes": [0],     // 下标指向 slotList
      "exams": [{ "courseName": "大学物理", "startPeriod": 2, "endPeriod": 4 }]
    }]
  }]
}
```

**为什么整张表在手机侧算好，而不是让网页端算**

一列是「这一周里的一个**真实日期**」，不是「星期几」——
补课只有在这一层才表达得出来：10-17 是周六，它要出周五的课，
而同一周的 10-16（周五）反而一节都没有。

哪些课落在哪一天牵扯四件事：开课周次、停课日、补课日、学期范围，
而这些规则在 App 里已经收口到 `ScheduleResolver` 一个地方了。
在网页端重写一份的代价不是「多写几十行」，而是**两边迟早给出不同的答案**，
而用户看到不一致时只会觉得网页端算错了 —— 他不知道手机那边有一份权威实现。

所以：**手机算好发过去，网页端只负责画。**
`snapshot.timetable` 为 null 表示「这一端还没有周课表」
（老版本 App，或课表还没生成过）—— 网页端据此把「周视图」那一档藏起来。

**载荷为什么长这样**

- **时段只存一份**（`slotList`），周计划里存下标（`slotIndexes`）：
  一门课在一学期里要出几十次，全文重复就是几十份一模一样的 JSON；
- **考试不重复**：一场考试只落在**一天**上，所以整张表里它只出现一次，
  内容直接内联进那一天。

### 快照里的原始校历（`calendar`）

周课表是**算出来的**，校历是**算它用的那本账**：学期起止、停课补课、作息时间。

只给 `timetable` 的话，网页端能画，但**画不出新的一周** ——
翻到第 14 周时它不知道那天是不是停课、不知道第 3 节几点开始。
所以快照里还带一份**原始校历**：

```jsonc
"calendar": {
  "termConfigs": [{ "Year": "2026-2027", "Term": 0, "Begin": 20260907, "End": 20261025, "FirstWeekNo": 1 }],
  "classTerms": ["2026-2027:0"],
  "tweaks": [{ "TweakType": "Clear", "Description": "国庆", "From": 20261001, "To": 20261003 }],
  "periods": [{ "period": 1, "startTime": "08:00", "endTime": "08:45", "section": "大教室" }]
}
```

- `Begin` / `End` / `From` / `To` 是 **`YYYYMMDD` 的整数**（不是字符串，也不是时间戳）；
- `tweaks` 是调休：`Clear` = 停课（国庆那几天），`Makeup` = 补课（周末上课）；
- `periods` 是作息表 —— 考试只有钟点，要落进第几节全靠它换算。

**网页端存下这一份，是为了写进它导出的 JSON。**
网页端导出的文件是**手机也认得的整机快照**（`schemaVersion = 4`），
有了校历，那份文件才能在手机上重建出正确的课表 —— 否则换机后周次对不上。

### 整机快照的顶层块（`schemaVersion = 4`）

手机 App 的「导出 JSON」与网页端的「导出 JSON」说的是**同一种东西**：
一份顶层分块的整机快照。两端都认它，所以文件可以**双向通用**。

| 顶层键 | 是什么 | 进 | 出 |
|---|---|---|---|
| `schemaVersion` | 版本号（现在是 4） | ✓ | ✓ |
| `provenance` | 这份文件是谁造的 | ✓ | ✓ |
| `calendar` | 原始校历（见上） | ✓ | ✓ |
| `timetable` | 课程与时段（`courses[].slots[]`） | ✓ | ✓ |
| `tasks` | 待办 | ✓ | ✓ |
| `taskTypes` | 自定义分类 | ✓ | ✓ |
| `taskRules` | 课程级生成规则 | ✓ | ✓（网页端没有这一块，留空） |
| `categoryRules` | 类别规则 | ✓ | ✓（网页端没有这一块，留空） |
| `exams` | 考试 | ✓ | ✓ |
| `weekPlan` | **渲染好**的周课表（只出不进） | ✗ | ✓ |

**「包里没有就别动」**：任一块缺空，导入时**那一块一条都不改**。
所以一份只带课表的文件（浙大同步产出的那种）导入进来，
不会把本机的考试抹掉。

### 冲突判定

冲突 = **同一条待办，两端都动过，而且动得不一样**。

| 情况 | 是不是冲突 |
|---|---|
| 对方没动过这条 | 否 |
| 对方也动了，两边内容一样 | 否（两边做了同一件事） |
| 对方也动了，两边内容不同 | **是** |
| 对方**没有**这条，而本地改过它 | **是**（一边改一边删） |
| 本地新建（`localOnly`），对方没有 | 否（还没推过去） |

冲突时**自动同步停下**，界面转成手动，并摆出**两端快照的最新编辑时间** ——
用户判断该往哪边同步，靠的是时间，不是「谁的条数多」。

## 6. 接口

除 `/api/health` 与 `/api/pair/` 下的接口外，全部要签名。

| 方法 | 路径 | 签名 | 密文 |
|---|---|---|---|
| GET | `/api/health` | 否 | 否（带 `pairing` 字段：配对协议版本，**≥5 = 协议 v3.2**，支持 DH 与转录绑定配对码） |
| POST | `/api/pair/request` | 否 | 否（此时还没有密钥） |
| GET | `/api/pair/status?requestId=` | 否 | 否（**里面没有凭据**） |
| GET | `/api/snapshot` | 是 | 是 |
| POST | `/api/snapshot/apply` | 是 | 是 |
| GET | `/api/zju/terms` | 是 | 是（响应） |
| POST | `/api/zju/sync` | 是 | 是（**请求体里有学号密码**） |
| GET | `/api/events` | 是（查询串） | 事件载荷是 |
| GET | `/…`（静态文件） | 否 | 否 |

**`POST /api/pair/request`**

```jsonc
{
  "requestId": "…",        // 这次配对的 id（base64url）
  "deviceName": "电脑网页端",
  "publicKey": "…"         // **可选**：电脑的 DH 公钥（base64url，256 字节）
}
```

- **带了 `publicKey`** = 「只填地址」那条路：手机当场协商出共享密钥，
  于是**立刻**就有东西可以弹确认卡了；
- **不带** = 「扫码」那条路：公钥在二维码里，手机扫到才会有。

**`GET /api/pair/status?requestId=`**

```jsonc
{
  "state": "pending" | "approved" | "denied" | "expired",
  "deviceId": "…",         // 批准之后才有
  "deviceName": "…",
  "publicKey": "…",        // 手机的一次性公钥 —— 电脑靠它算出同一把共享密钥
  "pairCode": "7K2M9Q"     // 配对码：电脑拿它跟自己算出来的一比
}
```

**这两个字段都不是凭据**：公钥是公开的（知道它也算不出共享密钥），
配对码是给人眼核对用的。

### 网页端请手机去学在浙大拉课表

浏览器**连不上浙大**：网页端是 `file://` 打开的单文件 HTML（Origin 为 `null`），
而学在浙大的登录链路跨三个域（`zjuam` → `zdbk` → `courses`）——
中间要自己读 302 的 `Location` 取 ticket、读登录页的 hidden input 拿 `execution`、
手改 TGC 的 Cookie Domain，这三件跨源脚本一件都做不到，
浏览器也拿不到浙大接口的 CORS 头。

所以这条路的形状是：**网页端把请求交给手机，手机去跑那套 CAS 登录**。
手机那边本来就有整套能力（`ZjuImportService` → `ScheduleSyncManager`），
凭据还躺在 Keystore 里。

**`GET /api/zju/terms` —— 可选的学期。**

- **不需要账号**：学期表是公共配置（浙大校历源）。
- 走签名鉴权；请求没有请求体，响应仍然是密文。
- 载荷：`{"terms":[{"year":"2026-2027","term":0,"label":"2026-2027 秋冬"}]}`
  - `term` 是教务网查询用的半学期：**秋冬 → 0（秋），春夏 → 4（春）**。

**`POST /api/zju/sync` —— 去拉一次课表（顺带拉考试）。**

请求体（**必须密文**，密文走 HTTP body + `X-ML-Enc: 1`）：

```jsonc
{
  "studentId": "3220000000",  // 可空 = 用手机已存的凭据
  "password": "…",            // 可空 = 用手机已存的凭据
  "year": "2026-2027",        // 可空 = 用上次同步的那一期
  "term": 0,                  // 可空 = 用上次同步的那一期
  "remember": true            // 是否把凭据转存进 Keystore
}
```

响应：

```jsonc
// 成功
{"ok":true,"courseCount":5,"slotCount":12,"examCount":2,
 "termLabel":"2026-2027 秋冬","savedCredentials":true,"examError":null}
// 失败
{"ok":false,"error":"学号或密码不对","kind":"AUTH","localDataIntact":true}
```

**凭据怎么走**：

- 网页端可以把学号密码填进来（第一次用时手机可能还没绑过账号）。
  那份密码**只在这次请求的密文里存在**（会话密钥派生的 ChaCha20，局域网上也解不开）；
- **网页端不记密码** —— 不落 localStorage；
- 手机这边在 `remember = true` 时**立刻转存进 Keystore**，下次就能免密拉；
- 不填就**用手机已存的凭据**拉 —— 那是手机 App 自己的那一份。
  只填了学号或只填了密码时按「没有凭据」处理（半填比不填更容易出事）。

拉完之后手机这边的 Room 变了 —— 广播会通知网页端重拉快照，
于是「用手机的课表和考试」拿到的就是刚拉回来的那份。

### 电脑端启动器的本地接口（旧版，已退役）

> 单文件桌面端**不用这些接口**；它们只属于旧的 `tools/pc-web` 启动器。
> 手机托管或新桌面端下这些路径不存在。

**不在上面那张表里** —— 它们是电脑上的本地服务提供的，跟手机无关。

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/__miulist/ping` | 启动器在不在（端口被占时用来判断「是不是我自己」） |
| GET | `/__miulist/target` | 手机在哪：`{"base":"http://192.168.x.x:端口","source":"discovered\|manual"}` |
| POST | `/__miulist/target` | 手动指定手机地址（网页端里填的地址存这里） |
| GET | `/__miulist/state` | 读本地镜像 |
| POST | `/__miulist/state` | 写本地镜像（网页端每次改动后防抖上传） |

镜像里含配对 secret，落盘时用 **Windows DPAPI** 加密（绑定当前 Windows 用户）。

### SSE 事件

| 事件 | 数据 | 什么时候 |
|---|---|---|
| `hello` | 密文 `{revision, protocol}` | 连上时 |
| `change` | 密文 `{revision, reason}` | 本机数据变了 |
| `sync-request` | 密文 `{direction}` | **手机让网页端去同步** |

`sync-request` 的 `direction` 是从**执行方（网页端）**的视角说的：

- `pull` —— 网页端去手机那边拉（手机 → 网页）
- `push` —— 网页端把它的推给手机（网页 → 手机）
- `merge` —— 两边合并

手机发 `sync-request` 是因为**浏览器不能监听端口**：手机推不动数据，
但手机可以**请求**网页端去做，方向由手机选。

## 7. 时间

**所有时间都由服务端算成字符串再发出去**，网页端不做时区换算：

- `today`、`dueDateString`、`timeText`、`whenText` 都是服务端时区（Asia/Shanghai）下的字符串；
- 网页端渲染「最后编辑时间」用 `utcOffsetMinutes`，**不用浏览器本地时区** ——
  否则用户会看到「本页 05:14 · 手机 21:14」，以为差了一整个晚上。

## 8. 安全边界

- 局域网内**任何**设备都能访问这个服务 —— 凭据只有每设备一把密钥。
- 授权发生在**手机上**（用户在确认卡上点「允许」）。
- **密钥从不过网**：两端用 DH 各自算出同一把共享密钥，
  线上跑着的只有公钥（见 §2）。抓包的人看到公钥也算不出密钥。
- **配对码**是用户核对用的：两端显示同一串 6 位码，不一致就说明
- 公钥被人换过（网页端还会**强制**比对并中止 —— 见 §2 的配对码）。
- **配对码是转录绑定的**：`H(A‖B)`，两端各自都算得出；
  网页端**强制**要求手机报上来的码存在且与自己算的一致，缺一即中止。
- **退化公钥一律拒收**（`0 / 1 / p-1`）——否则共享密钥会退化成公开常量。
- **传输是密文（应用层），不是 TLS**：
  - ✅ 抓包看到的是密文，拿不到待办内容，也伪造不了请求；
  - ✅ 已签名的接口，其响应**必须**带 `X-ML-Enc`；缺头即视为错误，
    不接受「降级成明文 JSON」（冒名服务器塞假课表的路因此堵死）；
  - ❌ 同网段的主动中间人仍能**阻断**连接（DoS），也能**改写请求**——
    改写会破坏签名或 MAC，被当场挡下；但「让它连不上」它做不到。
- **网页脚本不经过网络**：桌面端是**本地单文件 HTML**，双击打开；
  手机**不再托管网页页面**。所以「中间人替换 app.js 读走密钥」这条路不存在。
- 设备密钥**加密落盘**在手机本地（Keystore AES-GCM），它等价于共享密钥本身。
- 会话空闲 30 分钟即失效 —— 且**跨进程重启也照样失效**：
  上次活跃时间是持久化的，进程重启不会给它续命。
  每台设备可单独撤销。
- **跨源来源有白名单**：带 `Origin` 头但不在白名单里的请求**直接 403**。
  白名单 = 网页端的 `null`（file:// 单文件）+ `localhost`/`127.0.0.1`
  （本地开发）+ 手机自己的各个局域网地址。
  这样**互联网上的任意网页**既读不到响应，也发不出带自定义头的请求。
- **免鉴权端点有限流**：同一个来源 1 分钟内最多申请 5 次配对，
  待确认的请求同时最多 8 条 —— 否则任何人都能反复弹确认卡骚扰用户。
- 确认卡上显示的是**服务端观察到的来源地址**（`ip:port`），
  不是客户端自报的设备名 —— 后者谁都能写成「我的电脑」。
- 远端提交的浙大凭据**一律不写回**手机的 Keystore，
  且学号必须与手机已绑定的账号一致（不一致直接拒绝）。
- **旧启动器的本地镜像**（`web-state.bin`）含配对 secret，用 **Windows DPAPI** 加密：
  绑定当前 Windows 用户；这是旧版，新桌面端改为**不含 secret 的 JSON 快照**。
- **新桌面端的 JSON 快照**含课程/待办/考试，**不含配对密钥**；secret 只在浏览器
  localStorage。快照是明文个人数据，请像备份一样保管。
- **UDP 发现口**（`38777`，旧启动器用）会告诉局域网里的设备「这里跑着 MiuList、
  它的 HTTP 端口是多少」。泄露的是**地址**，不是**内容**；数据仍要配对、签名才能读。
- **扫网段找手机**（浏览器那条路）也只暴露**地址**：`/api/health` 里
  没有密钥，也没有任何待办内容。
